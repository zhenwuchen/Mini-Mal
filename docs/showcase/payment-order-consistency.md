# 支付与订单一致性设计

## 1. 业务不变量

当前实现重点保护以下不变量：

- 一个订单最多只有一个成功支付；
- 支付金额与币种必须匹配订单；
- 非待付款订单不能完成支付；
- 已成功支付不能再次失败或重复完成；
- 取消待付款订单时必须恢复库存，且只能恢复一次；
- 有成功支付时不能直接取消订单；
- 支付截止时间之后不能完成支付；
- 订单、支付和库存变更必须作为整体提交或整体回滚。

## 2. 支付状态机

允许的迁移：

```text
PENDING -> SUCCEEDED
PENDING -> FAILED
PENDING -> CANCELLED
SUCCEEDED -> REFUNDED
```

其他迁移均被拒绝。状态机定义位于 `src/lib/payment-status.ts`。

## 3. 支付幂等

发起模拟支付需要 `idempotencyKey`：

1. 在事务中按 provider 与幂等键查找已有支付。
2. 已有支付且属于当前订单时，校验金额、币种和方法后返回原记录。
3. 已有支付属于其他订单时返回状态冲突。
4. 数据库中 provider + idempotencyKey 的唯一约束作为并发兜底。
5. 唯一约束竞争发生后，重新读取并返回唯一合法记录。

同一幂等键不会重复创建支付，也不会重复改变订单。

## 4. 并发完成保护

并发完成支付时，仅依赖“先读后写”不足以保证只有一个成功结果。当前实现同时
使用：

- Prisma Transaction；
- 带 `status = PENDING_PAYMENT` 条件的订单更新；
- 带 `status = PENDING` 条件的支付更新；
- 成功支付数量检查；
- SQLite 写锁冲突的有限重试；
- 事务内最终状态重新读取。

并发请求中未取得状态更新的请求会重试或返回冲突。测试验证两个并发尝试最多
只有一个成功，数据库中成功支付数量为 1。

## 5. 支付截止时间

订单创建时写入：

```text
expiresAt = createdAt + 30 分钟
```

完成支付时，最终订单更新使用数据库执行时间：

```sql
status = 'PAID'
AND (
  expiresAt IS NULL
  OR expiresAt > current_database_time_ms
)
```

应用注入时钟用于测试和早期校验，最终截止边界由数据库执行时间决定，避免
应用进程时间偏差或写锁等待跨过截止时间后仍完成支付。

历史订单 `expiresAt = null` 保持可支付；新订单均写入明确的截止时间。

## 6. 订单取消一致性

取消流程在同一个事务内：

1. 条件更新待付款订单为已取消；
2. 查询是否存在成功支付；
3. 取消待处理支付；
4. 按订单明细恢复库存；
5. 提交全部变更。

如果库存恢复失败或发现成功支付，事务回滚，订单不会只取消一半。
重复或并发取消通过订单状态条件和事务收敛为一次库存恢复。

## 7. 失败与重试

Service 对 SQLite 锁冲突、事务关闭、事务竞争等可重试错误最多尝试 5 次。
重试只用于瞬时写入竞争，不用于业务状态错误。永久失败返回受控错误码，
避免暴露 SQL、Prisma 内部信息或堆栈。
